# Private thread tickets

This is a separate support flow from existing private channel tickets. It creates only bot-owned private threads under one explicitly approved ordinary server text channel. It does not change existing channel-ticket metadata, transfers, priorities, ratings, panels or workflows.

A manager with Manage Server uses `ticket.thread-configure` to select a parent and one to five current staff user IDs. Each staff member must currently have Moderate Members or the configured community staff role, and must be able to view/use the parent. The bot needs View Channel, Create Private Threads, Manage Threads, Send Messages in Threads and Read Message History there. The configuring manager must remain a member with Manage Server and current parent access.

Members read `ticket.thread-settings`, review the parent/staff audience, then confirm `ticket.thread-open` with a subject and the exact returned `configurationVersion`. The request always belongs to the invoking member. An older version cannot silently use a newly configured audience. The owner needs parent View Channel and Send Messages in Threads; public threads and arbitrary parents are not accepted.

The thread has a random 96-bit `support-<reservation>` name, `PrivateThread` type and `invitable: false`. Subjects and owner identities are not placed in the thread name. The durable record and active-owner reservation are saved before Discord creation. Once Discord returns the real thread ID, it is saved before inviting anyone. The owner and approved staff are then added individually with current membership, parent access, staff eligibility, action policy, configuration and bot permissions rechecked. No extra participant IDs are accepted.

Each member has at most one active or unresolved thread-ticket reservation, and at most ten new requests per UTC day. There are at most 500 active tickets and 5,000 retained ticket records per server, and 25,000 records overall. Concurrent owner requests use one lock. A failed or lost creation response becomes `needs-review`, and a persisted interrupted creation also requires review. Creation is never automatically retried.

`ticket.thread-reconcile` lets current approved staff bind the actual private thread after checking server, parent, exact unique name, bot owner and `invitable: false`. Reconciliation does not accept public threads or arbitrary existing private threads. Manage Server can separately acknowledge that no thread exists only after two minutes, explicit manual server-state review, and bounded active/archived inventory checks. An existing exact match blocks absence release. If the archived private inventory exceeds one complete 100-item page, the reservation remains unresolved for manual investigation; the bot does not claim that an incomplete scan proves absence.

Invitations are idempotent and persist individual progress. Transient invitation failures retry with backoff at most three times; authorization/configuration failures stop immediately. `ticket.thread-retry` retries only pending invitations on an already known thread under the unchanged reviewed configuration. It never creates a new thread. Module pauses and allowed-server restrictions stop queued external work. Changing parent/staff configuration stops old pending sharing.

`ticket.thread-view` and `ticket.thread-list` disclose only owner/current approved staff records with current parent and private-thread access. `ticket.thread-close` requires the owner or current approved staff and current private access, then locks and archives the exact managed thread. It never deletes messages or threads. A successful close releases the active-owner reservation. An uncertain close retains its known ID and can safely be explicitly repeated. Closed metadata is removed after thirty days; Discord threads remain intact.

`ticket.thread-transcript` exports a bounded, explicitly partial text attachment containing at most one hundred recent messages. Both caller and bot need current message history permission. Membership, current staff eligibility, parent visibility, private-thread access and history permissions are checked again after fetching. Older/deleted messages and attachment contents are omitted. This is not a complete historical archive.

Discord owners and members with Manage Threads/Administrator can have native access beyond the selected participants. The bot's action authorization does not revoke previously granted native thread membership when a staff member later loses their staff role; server staff must manage that membership through Discord. Subjects/records and private thread content remain distinct data with separate retention. No OAuth, anonymous submission, external storage or generic private-thread administration is provided.

Offline tests cover approved audiences, exact configuration review, private reservations, missing/stale permissions, concurrency, unknown-create recovery, bounded invitation retries, mid-flight revocation, closure, partial transcript checks, quotas and metadata retention. Live Discord acceptance remains an operator task.
