# Voice playback and consented AI

Enable `ENABLE_VOICE=true` to register the voice actions. Playback is bounded, and receiving audio requires each speaker's explicit consent. AI speech is synthetic. Generated speech, spoken translation, conversational replies and meeting summaries use the configured OpenAI key and quota controls. Transcription can run locally; the optional OpenAI transcription backend uses that same key.

Disabling `ENABLE_VOICE` removes those audio actions. The bot still receives voice-state metadata for separately configured room automation and opt-in analytics; that Gateway subscription does not join a channel or capture audio.

## Start speaking

1. Join a voice channel and run `/join` from a text channel you can read.
2. To make Vibe read one message, run `/speak text:Hi, I am Vibe.`. Direct ordinary requests execute immediately under smart confirmation mode; an installation using always-confirm mode still displays its normal preview.
3. For a spoken conversation, run `/consent replies:true` in the original command channel or the disclosed private transcript channel. Only your own subsequent voice is eligible for transcription and spoken replies. Other speakers need their own consent and access to that private destination. Consent expires after ten minutes; `/revoke` or leaving immediately withdraws it.

Joining alone never starts listening or enables AI replies. `replies:false` grants transcription without a spoken answer. Production voice joining requires a verified dedicated private transcript channel and has no public fallback. The join/consent responses disclose that destination. The original command channel never receives captured transcripts simply because `/join` was used there.

Address **Vibe** in a new request, for example “Vibe, change the server name to W” or “Can you help me, Vibe?” Clear comma-delimited direct address in the middle of a request also works. Third-person references such as “I told Vibe” and “Vibe is offline” do not start a conversation. For the Vibe name, limited transcription variants (`bibe`, `vybe`, `vibes`, `five`) are accepted only before a clear direct request; bare variants, numeric phrases such as “five hours,” and ordinary “bye” are ignored.

After you address Vibe, the same consenting speaker can continue a conversation and ask tasks without repeating its name on every turn. The idle window defaults to sixty seconds after the spoken response, configurable within 5–60 seconds. “It’s going good, how about you?” can answer “How’s your day?” naturally. Another speaker needs their own consent and wake; explicitly other-directed speech does not renew attention. Say “bye,” “that’s all,” or “stop listening” to close the conversation. Continued turns remain bounded by the original ten-minute listening consent. After the idle window expires, say Vibe again. A bare recognized name receives “Yes?” and opens attention. Stop, revoke, departure, consent renewal and session replacement invalidate prior turn state. Speaker-reset hooks also clear the host’s idle Realtime/text conversation context. Every voice request has authority tied to its exact session, consent token, speaker and private destination.

The durable session stores identity rather than the temporary authorization from `/join`. Captured speech creates fresh voice authority, so moving output into the private transcript channel or expiration of an old join command cannot reject a valid spoken reply. Explicit `/speak` retains its own command authority. Pure quoted conversational commands cannot reach deterministic confirmation controls or AI mutation tools; a specifically requested message-body clarification remains separately restricted to posting that dictated content.

“Vibe, type in general and say” goes to the Discord action planner. With no dictated body, it asks “What should I say in #general?” once. The same speaker can supply a short message within the active window; quote it or start with “say” when its words resemble a new command. That answer is message data: even literal “confirm,” “cancel,” or “delete all roles” cannot confirm or execute an unrelated action. Missing bodies cannot become punctuation-only or invented posts. Role-color requests also use the planner; a misheard “rule” can resolve to a real role, with one clarification if names are ambiguous. Discord still protects managed roles and roles at or above the bot’s highest role, including from an Administrator bot.

For “send a bunny GIF to general,” the planner can search the configured Wikimedia Commons catalog and send an exact returned result into that visible channel with attribution. It can choose a relevant result for an ordinary request instead of demanding an uploaded file. The search token remains bound to its original requester/channel, and destination permissions are checked separately. No extra key is required for this catalog; it does not claim Tenor/Giphy coverage.

Name detection is applied to consented transcriptions. The local transcription backend processes utterance audio on this host; addressed requests and explicitly requested AI summaries/translation text can then be sent to OpenAI. An installation selecting the OpenAI transcription backend sends consented utterances to that provider even when Vibe does not answer. Both backends log transcripts only in the private destination. This is transcript-based name detection rather than an acoustic wake-word claim.

`OPENAI_SPEECH_MODEL` selects the speech model and `OPENAI_SPEECH_VOICE` is the single active voice setting. The default voice is `marin`; both `marin` and `coral` are supported by `gpt-4o-mini-tts`. Older installations may contain the legacy `OPENAI_VOICE` name; migrate its chosen value into `OPENAI_SPEECH_VOICE` and remove the obsolete line. Restart after configuration changes. The [official text-to-speech guide](https://developers.openai.com/api/docs/guides/text-to-speech) describes the supported voices and PCM output.

## Streaming response path

The native driver accepts a real streaming PCM source. When the host supplies a realtime reply adapter, generated 24 kHz mono PCM16 chunks are resampled incrementally into Discord’s 48 kHz stereo PCM16 and the Opus/volume pipeline starts on the first chunk. Byte/sample boundaries are preserved across network packets. The service serializes concurrent adapter callbacks, applies playback backpressure and bounds generated audio to two minutes. It does not wait for the full answer or perform a second text-to-speech request for already generated audio.

Stop/revoke, membership departure, module disablement, session change and invalidated private-channel permissions cancel the stream. Late chunks cannot revive it. Drivers without streaming support receive the same bounded generated audio through a buffer fallback, without re-synthesizing it. An action-like request can decline the realtime path before emitting audio and use the normal tool-capable text/action path instead.

After generated speech is complete, a playback watchdog waits for its predicted remaining PCM duration plus ten seconds. If the transport never emits Idle, it stops that stale track, clears the affected voice follow-up context and releases the queue/capture path with a `playback.stalled` diagnostic. Intentional pause and transport recovery suspend this playback clock; resume preserves the remaining duration. Idle, stop, revoke and leave cancel the watchdog. Unfinished generation and ordinary music/media playback are outside this guard, and it never extends consent.

The provider's audio-complete event now flushes and ends the PCM source before private response delivery. Permission checks use the exact cached speaker/session lease per chunk, with forced checks at stream boundaries; audio chunks no longer wait for repeated REST fetches. The native player tolerates up to fifty missed 20 ms frames. Idle before generation completes cancels that source immediately rather than leaving a writer waiting for a destroyed player. Adapter stages and private delivery have cancellation/deadline bounds, and an aborted request releases capture before its separate short failure notice. Stop/revoke signals also reach the local worker and OpenAI calls. Known completed changes remain acknowledged if later delivery or speech fails and are never automatically replayed.

Private transcript/reply sends pass cancellation into Discord's actual REST queue. Cached channel, role and membership updates recheck authority while a send is queued; an invalid lease aborts it before dispatch. A queue deadline also prevents delayed delivery after the request expires. `request.lease-rejected` diagnostics record a reason code without speech content, distinguishing cancelled requests, membership, permissions and private-channel invariants.

The default native utterance silence threshold is 450 milliseconds, configurable from 250 to 1500 milliseconds. Ambient speech is filtered before conversational generation, and a completed voice command skips the second generic reply. Fresh member/channel checks are retained without duplicate identical REST lookups at each capture stage. Provider/network latency and the end of the speaker’s utterance still affect response time.

Transient Discord connection changes now receive a bounded opportunity to finish the SDK’s reconnect sequence. A disconnected connection has five seconds to enter Signalling/Connecting and up to twenty seconds to become Ready; an already reconnecting connection receives the Ready deadline. Capture pauses while the transport is unavailable. Explicit leave, kick/membership loss, disable and shutdown still discard consent/session authority and cancel recovery. The host never forces a rejoin after a real removal. This follows the [Discord.js connection lifecycle guidance](https://discordjs.guide/voice/voice-connections).

## Diagnosing a silent voice session

Read `voice.status` through `/action` to distinguish active capture, provider processing, playback, pause and transport recovery. Its in-memory counters show captures, completed transcriptions, addressed requests, ignored wake/follow-up candidates and failed requests. The optional `onDiagnostic` hook emits lifecycle stages and timing/counter metadata to the runtime log without speech, transcript contents, names, credentials or audio. Capture skip reasons are throttled to one event per ten seconds.

`wake.ignored` distinguishes an unrelated candidate inside an active follow-up from speech without a recognized name or active follow-up. `access.denied` indicates current permission validation failed; `processing.failed` identifies quota, transcription, Realtime or general processing failure. A quota/provider failure can issue a throttled notice only in the verified private transcript channel. The capture lock is released after error handling. No silent provider replay or remote fallback is added.

There is no one-minute conversation expiry. Tests cover forty streamed turns across several minutes, clean Realtime context rotation after 32 turns, reconnect deadlines and the original ten-minute consent expiry. Live recognition, network connectivity and permission changes still need their corresponding runtime evidence.

## Loading and portability checks

`pnpm run doctor` now executes the real raw PCM → volume → Opus → decoded PCM pipeline and creates a native DAVE session/key package. It reports the selected working codec. Missing optional alternatives such as `@discordjs/opus` or sodium libraries do not indicate failure when the installed `opusscript` fallback and native AES-GCM pass those executable checks. Add `--dependencies` for the library's detailed alternatives report, or `--voice` to probe voice explicitly when audio is disabled.

The first real connection also validates the codec and native DAVE runtime before opening a transport. Voice packages load lazily: a broken native library produces a voice-specific repair error and does not prevent non-voice service construction. Install frozen dependencies on the destination computer; do not copy `node_modules` between operating systems or CPU architectures. Dependency resolution is relative to installed modules and is tested from a working directory outside the project. A working local pipeline cannot verify Discord UDP connectivity, permissions or a live encrypted voice session; those still need test-server acceptance.

`MAX_VOICE_SESSIONS` defaults to five connected or joining servers and accepts integers from one to twenty. The service reserves a slot before opening a transport and releases it after failed/cancelled joins or disconnects. Each session can hold up to 24 MiB of current/queued decoded audio, plus bounded processing buffers and transport/codec state. Raising the session cap requires additional RAM and CPU; the upper configuration bound is not a claim that twenty active sessions fit the default deployment resource budget.

`voice.join` joins the caller's voice channel. Both the caller and bot need View Channel, Connect and Speak there. A Stage additionally requires both to be moderators with Mute Members; the bot unsuppresses itself after joining. `voice.move` reuses the transport to move to an authorized voice/Stage destination, clearing previous audio and consent. `voice.status`, `voice.pause`, `voice.resume`, `voice.skip`, `voice.volume`, `voice.stop` and `voice.leave` control that server's session; controls require the caller to be in the bot's voice channel. Volume changes current and subsequent playback without restarting a track. Stop clears queued audio and invalidates pending speech, uploaded playback, playlist playback and meeting summary results. Leaving/disable/shutdown discards the session and transport.

`voice.play` selects a supported audio attachment from a message in the current text channel. Inputs are at most 8 MiB. PCM16 WAV uses the local validated reader; MP3, FLAC, Ogg/Opus, M4A/MP4, WebM and other supported compressed WAV use the bounded FFmpeg pipeline. Output is 48 kHz stereo PCM for at most 120 seconds: known overlong inputs fail, and streamable inputs with unknown duration are clipped to that bound. `voice.speak` generates up to 1,000 text characters of synthetic speech. The queue allows five waiting tracks and at most 24 MiB of current plus queued decoded audio.

`VOICE_STREAM_SOURCES_JSON` optionally maps fixed safe IDs to operator-approved public HTTPS audio sources, for example `{"station":"https://media.example.org/clip.mp3"}`. Blank configuration disables those sources. `voice.sources` lists IDs and hosts; `voice.stream` accepts only one of those IDs. Fetching uses public-address validation and a 2 MiB response cap; decoding has the same 120-second bound. These are bounded audio segments rather than an unlimited live radio connection. Requests never accept user-supplied paths or arbitrary stream URLs.

`voice.queue.saved` inspects durable music references, `voice.queue.restore` explicitly reauthorizes and restores them, and `voice.queue.clear` erases them. The current track and waiting music references survive an orderly shutdown in SQLite; PCM bytes, speech, signed attachment URLs and consent do not. Interrupted tracks restart from the beginning. Restore validates every message/local/source reference against current configuration and permissions before atomically admitting the queue. Explicit stop/leave clears saved references.

## Approved local audio and alerts

`VOICE_AUDIO_DIRECTORY` optionally identifies a fixed operator-approved WAV directory. Its empty default disables the local library. `voice.library` lists up to fifty eligible file IDs, scanning at most one thousand directory entries. `voice.library-play` accepts only a lowercase ID containing letters, digits, underscores or hyphens, up to 32 characters; `{"id":"chime"}` selects `chime.wav`. Users cannot supply paths, URLs, extensions or another root.

The reader resolves the configured root and selected file with `realpath`, rejects targets outside that root, checks regular-file identity and size around opening, and reads at most the stated size plus one byte. The same 8 MiB PCM16 WAV and 120-second playback bounds apply. Local playback shares the one-per-server/two-global file-processing limit with playlists and refreshes voice membership, voice permissions and text history access before and after file work. Stop, disconnect, disable, shutdown or membership loss discards late playback.

`voice.alert` queues a deterministic `notice`, `success` or `warning` tone. These short stereo PCM tones use no AI request or external file and obey current voice authority and the normal queue bounds.

## Spoken trivia

`voice.trivia-start` speaks one of eight fixed known-answer questions, optionally selected with `questionId`: `arithmetic`, `japan`, `triangle`, `planet`, `ocean`, `water`, `minutes` or `hexagon`. Start requires idle, resumed voice playback. The question is returned as text as well as queued for synthetic speech, and answers remain open for sixty seconds after it is queued.

`voice.trivia-answer` submits a bounded answer for the current question. Answers are matched against fixed normalized aliases; no model judges or generates answers. Each participant gets three guesses, the first correct answer earns one point and closes the question, and at most twenty-five participants can be tracked/scored per session. `voice.trivia-status` reports the question, expiry and session scores without exposing an open question's answer. `voice.trivia-stop` clears the game/scores and stops voice playback. Typed playback and trivia mutations use the normal registry confirmation flow.

Games require current membership of the bot's voice channel and access to the text channel where they started. Questions/scores are held only in memory, bounded to one session per server and one hundred servers; scores expire after thirty minutes. Stop, disconnect/reconnect and session replacement invalidate old game revisions. Invalid or expired state is pruned on the next trivia operation. These are local session scores, not an external game statistics service.

## Persistent personal playlists

`voice.playlist-save` validates 1–5 supported audio attachments from the current text channel and saves only their message/channel references and titles. No media bytes or signed attachment URLs are stored. A playlist must fit the 24 MiB decoded-audio budget. Each user can save ten playlists per server, with fifty per server overall. Names use lowercase letters, digits, underscores or hyphens, up to 32 characters.

`voice.playlist-list` shows the caller's saved names/counts; `voice.playlist-remove` deletes one. `voice.playlist-play` resolves each source message again, checks the caller and bot can view/read its history, downloads the currently authorized Discord attachment, rechecks permissions/session/version, and queues the whole playlist atomically. Insufficient queue capacity adds no tracks. Removed messages, revoked source permissions, deleted/changed playlists, stop, leave, disable and shutdown prevent late playback. Playlist processing is limited to one operation per server and two globally.

## Individual transcription consent

Run `voice.consent` with `enabled:true` in the original command channel or disclosed private transcript channel. The private channel remains the fixed transcript destination for that session. Consent lasts ten minutes and covers only that speaker's future utterances, at most fifteen seconds each. Raw PCM is bounded in memory and discarded after transcription by the selected local/OpenAI backend. Transcripts are posted only to the dedicated private text channel with mentions disabled. Its permissions must explicitly deny View Channel to @everyone and cannot grant ordinary roles broad access. The verified bot managed role and selected member overwrites are supported; Discord administrators retain their platform-level access. Capture requires current voice membership, current voice permissions and View Channel/Read Message History access to the text channel for both the speaker and bot. Consent/session/access are checked again before publishing a completed transcript. Only one utterance is captured/processed per server at a time. Capture pauses during bot playback and while paused.

`vad:true` separately enables local acoustic energy detection. Twenty-millisecond RMS frames distinguish silence from active audio before transcription or archiving; `voice.activity` exposes only the caller's last opted-in acoustic metrics. This is energy-based VAD and can treat loud non-speech as active audio. It does not claim to identify speakers or interpret speech acoustically.

`voice.recording.configure` lets a manager explicitly enable individual WAV archives, choose retention of 1–168 hours and a limit of 1–100 utterances per server. The archive is disabled by default. A speaker must separately set `recording:true` in their own consent. Set `transcription:false` for local recording only, without an OpenAI upload; that mode cannot also request replies, commands, meetings or translation. Only that speaker's bounded utterances are saved, rather than a mixed room recording. Consent renewal is required after a recording-policy version changes.

`voice.recordings.list` lists your unexpired files, `voice.recordings.export` returns one of your own WAVs after fresh source-channel history authorization, and `voice.recordings.erase` revokes your current voice consent and deletes your archive and acoustic metadata. Erasure also invalidates a waiting export. SQLite holds at most 64 MiB of raw archive data across servers; admission also enforces per-server count and retention. Startup and periodic expiry remove expired rows. Ordinary consent revocation stops future capture and pending delivery; separately saved files remain until expiry or explicit erasure. Host operators and backups can access stored audio, so protect the database and backups.

Optional `replies:true` enables name-triggered conversational synthetic replies. The application can route authorized actions through the same typed registry, actor permissions, current policies and applicable confirmation mode as text. `enabled:false` revokes consent immediately and discards pending results, queued/current consented speech and retained meeting excerpts for that speaker. Moving/leaving voice, expiry, disconnect, module disable or shutdown also revoke consent. A request already sent to an external provider cannot be recalled, but late results are discarded after revocation. Speech generation refreshes membership/authority before provider upload and before playback.

`commands:true` separately enables deterministic voice controls without enabling conversational AI. With conversational replies enabled, the host can also route addressed action/confirmation requests through `VoiceOptions.onTranscript(ctx,text)`. This callback receives the current consenting speaker and private destination; it returns a payload rather than posting it. A handled command is delivered once and skips generic conversation, avoiding duplicate actions and redundant model work. The service rechecks consent, session generation, membership and private destination before publishing. Optional `voiceResponse` and `followUp` payload metadata provide concise spoken feedback and bind a real pending confirmation to the speaker’s active turn.

The conversational callback receives a bounded `VoiceTurnMeta` containing the previous request/response only for an admitted follow-up. An empty response suppresses speech and does not extend the conversation. Personal text-chat preferences and administrative identity from another user are never borrowed. Translation and meeting summaries remain separate stateless callbacks without administrative tools.

Personal conversation erasure also resets that speaker’s voice follow-up window, provider context and generated audio, removes their meeting excerpts, and invalidates pending voice requests. Their consent keeps its original expiry; other speakers’ consent and playback are unaffected.

An optional `language` opts into translating addressed utterances and speaking that translation. Original consented transcripts continue to use the private destination; ambient utterances do not trigger translated speech when name gating is enabled. Supported language codes are `en`, `es`, `fr`, `de`, `it`, `pt`, `ja`, `ko`, `zh`, `ar` and `hi`; omission disables translation. For example, `{"enabled":true,"language":"es"}` opts into sending addressed transcript text for translation; audio uses the selected local/OpenAI transcription backend and original/translated text appears only in the private transcript channel. Translation requires both `VoiceOptions.translate(ctx,text,language)` and speech adapters. Translated output is bounded to 1,000 characters and is posted/spoken only after fresh consent, session, voice membership and View/Read Message History checks. The same checks run again before speech upload and after synthesis; revocation removes queued consented translation/reply audio as well as preventing late provider results.

## Optional meeting excerpt summaries

The additional `meetings:true` consent option explicitly opts the speaker into a bounded in-memory meeting excerpt. It defaults to false. This adds no full-session recording. The buffer contains at most 6,000 characters, sixty utterances and ten speakers, and retains only excerpts from currently active, unexpired meeting consent tokens. Renewing/revoking consent or leaving removes the corresponding excerpts; stop and session destruction clear the buffer.

`voice.meeting-status` shows excerpt counts. `voice.meeting-summary` returns a private summary attachment using the supplied AI summary hook. It is available only from the disclosed transcript text channel to a current voice participant. Before and after the AI request, the requester and every source speaker must still be human members in the same voice channel, with View Channel/Read Message History in the destination, and every source consent token must remain valid. Any relevant change aborts the result. Only one summary per server may be generated at once. The summary hook must use no administrative tools, personal preferences, or retained conversation history; the application wiring follows that contract.

Tests cover actual Opus encode/decode, PCM/WAV validation, connected/joining session caps, isolated queue bounds, source history access, playlist persistence/atomicity, consent expiry/revocation, current participant checks, excerpt bounds, command opt-in, translated speech, fixed-answer trivia and delayed results after stop/revoke/departure/disable/shutdown. Local-library tests read real temporary WAV files and verify size/type/duration/path bounds. The escape test uses a real file symlink where permitted and a Windows directory junction named `escape.wav` otherwise; it asserts the outside-root boundary error before file-type checks. No live Discord, OpenAI or authenticated provider calls are required by these tests.

`voice.attendance.report` requires Manage Server and exports retained observed member voice durations as CSV. Supplying `eventId` instead delegates to the existing local calendar attendance exporter, including its source-access checks. These reports reflect opt-in observations/check-ins; they do not reconstruct downtime, missed events or past channel history.
