# Native event channel lifecycle

`eventchannel.configure` binds one native Discord scheduled event to one new private text channel. A confirmed manager selects an existing category, up to twenty ordinary visibility roles, minutes before the scheduled start to open, and minutes after the scheduled end/completion/cancellation to archive. Events and local `calendar.*` entries remain separate.

The configuring member must currently have Manage Events, Manage Channels and Manage Roles. The bot needs Manage Channels and Manage Roles. Both need current view, send, history and channel/overwrite management access in the selected category. Every selected role must remain ordinary, manageable and able to view that category. The parent category, author membership, roles, bot permissions, origin channel and configuring action policy are rechecked for each due operation.

The created channel denies everyone visibility and sending. Only the selected roles, configuring member and bot receive explicit access. Thread creation and thread sending are denied. Server owners and Administrators retain Discord's permission bypass. The policy does not grant roles, invite users, send DMs or create threads.

The sweeper fetches the native scheduled event again on every due cycle. Rescheduling changes its opening/closing boundary. If the bot missed the whole event or observes cancellation/completion before opening, no late channel is created. If no scheduled end exists, closure waits until Discord reports completion/cancellation; the first observation supplies the end reference. Otherwise the earlier known scheduled end/terminal observation supplies the closing reference. Polling, downtime, native API availability and retries can delay work.

Closure renames the channel to `archived-event-<policy ID>`, hides it from participant roles, and denies sending/thread creation while retaining history for the configuring manager and bot. No channel or message is deleted. Exact topic reservation, parent/type and original expected permission overwrites must still match. Unrelated permission edits stop closure for manual conflict review instead of overwriting staff changes. An interrupted close can recognize the identical archived permission state safely.

Creation saves a unique 96-bit reservation and `creating` state before calling Discord. Any create error, including a lost response, becomes `needs-review`; no automatic create retry occurs. A persisted interrupted `creating` state also requires review. `eventchannel.list` displays the exact topic marker and reservation. After inspecting server state, `eventchannel.reconcile` can attach the real matching channel or acknowledge that none exists. The latter requires at least two minutes, a fresh guild channel listing with no matching marker, explicit reviewed-state acknowledgement, and a new reservation. Reconciliation is bound to the same server, category, text-channel type and expected overwrites.

`eventchannel.pause` stops future operations while preserving channel/reservation tracking. Pausing an already submitted creation cannot recall Discord's request, so its returned channel ID is still retained. `eventchannel.retry` explicitly resets a failed nonambiguous operation after review. `eventchannel.remove` cancels an unopened waiting policy or forgets closed metadata; it cannot discard an active or uncertain creation and never deletes a channel.

State is durable SQLite data. There are at most 25 policies per server and 500 overall, ten due policies per sweep, a per-policy operation lock, and three attempts with backoff for noncreation failures. The allowed-server list and module pause are respected. Failed/unknown outcomes remain inspectable. A configuring manager who leaves or loses authority stops automation; this module does not transfer ownership automatically.

Offline validation exercises boundary timing, rescheduling/cancellation, private overwrites, authorization revocation, module/action policies, concurrency, unknown-create reconciliation, crash recovery and permission conflicts. Live Discord lifecycle acceptance remains an operator task.
